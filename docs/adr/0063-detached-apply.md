# 0063: Apply runs on the box, detached from the laptop

Date: 2026-11-09. Status: accepted. Amends ADRs 0008 (Ctrl-C over SSH), 0025 and 0049 (how an apply runs over SSH).

## Context
`keelbox up`, `apply` and `create` upload keelbox and run `keelbox apply` as root on the box. A first apply takes minutes. Run inside the laptop's SSH session, it would stop after its current step when the laptop slept, the window closed or the network dropped. Nothing would be half-done, but the box would not be set up either, and the owner would have to keep the laptop open and online for the whole run. Setup should carry on on the box without the laptop, and keelbox should pick up its progress and report on it on return.

## Decision
- **The apply is a transient root unit.** Over SSH, apply's remote script runs `keelbox apply --local` with `KEELBOX_DETACH=1`. That process takes `/run/keelbox-start.lock`, and if a run is active prints its id; otherwise it copies the staged config to `/run/keelbox/run-<id>.yaml`, starts `systemd-run --unit keelbox-apply-<id> --collect -p KillMode=mixed -p TimeoutStopSec=5min` with `KEELBOX_RUN=<id>`, and prints `keelbox-run: started <id>`. The unit keeps only `PATH`, `HOME`, `LANG`, `SUDO_USER` (and its ids) and `KEELBOX_SSH_CONNECTION` from the sudo that started it, so the bootstrap account's deferred steps and the tailnet proof (ADR 0021) work. The unit's process is an ordinary apply: it takes the apply lock (ADR 0030), runs the downgrade guard and the first-apply gate, and writes the logbook. Starting needs root once: `sudo -n` for an account with key sudo, the `ssh -t` sudo of ADR 0049 for one whose sudo asks for a password. The run id is the UTC start time and four random hex digits; the box is implied, since the unit lives on it.
- **Run log.** The unit writes `/var/lib/keelbox/runs/<id>.jsonl`: a `start` record (box, keelbox version, who started it, its modules), `module` and `step` records parsed from apply's own log lines, a `module-done` tally per module, `out` and `err` records for every other line, and an `end` record with the logbook's result, counts and exit code. `current` names the newest run. Directory 0750 and files 0640, `root:sudo`: the admin and other accounts with sudo can read them without sudo, the agent cannot. Text goes through `plain.Text` and is cut at 2000 characters; past 4 MiB only tallies and the result are written (the journal still has everything). The ten newest logs are kept.
- **The laptop follows the log.** After the start, the laptop runs `tail -c +OFFSET --pid=MAINPID -f` on the log over SSH, as the account it logs in as, and renders each record back into the line apply would have printed, into the same progress view or plain output. Live display, `--verbose`, non-terminal output and exit codes are those of an apply run in place when nothing goes wrong. The ssh runs in its own process group, so Ctrl-C reaches only keelbox.
- **Losing the laptop does not stop the run.** A dropped stream is retried: the laptop asks the box for the run's state every 5 seconds for up to 3 minutes, says when it lost and regained the connection, and carries on from the byte it had read. A run that is no longer active and has no end record died (the box restarted, or the process was killed): the laptop says so, with the step it reached and the command that carries on.
- **Ctrl-C asks.** On a terminal: leave it running (the default) or stop it after the current step. Stop sends SIGINT to the unit's main process (`systemctl kill --kill-whom=main`, with `sudo -n`, or `sudo` on the terminal for a password-sudo account), which apply takes as it takes Ctrl-C: the step finishes, the logbook records `interrupted`, exit 130. A second Ctrl-C after asking to stop leaves. Without a terminal, at SIGTERM and when the terminal closes, keelbox leaves without asking. Leaving exits 4, with the command that picks the run up.
- **Rejoin.** `keelbox apply`, `keelbox up` (whose stages call apply) and, on a terminal, `keelbox status` first read the box's newest run. A running one is followed from its start, replayed through the view with each record's own time, so a second apply while one runs attaches instead of starting another. A run this machine started or followed and did not see end is in `~/.config/keelbox/boxes/<box>.run.json`; when it has finished, its result is reported once (`setup on acme finished 6 min ago: 31 steps, 24 changed, ok`) and the apply returns that result instead of applying again. A run that died is reported, and the apply starts a new run, which carries on from the first step not in place.
- **Laptop-only steps stay on the laptop.** Hetzner API calls (the server, the Cloud Firewall), the tailnet proof that closes public SSH and the sign-ins run around the applies, on the laptop. Because rejoin happens inside the apply, every step after it runs when the user comes back: `up` resumes at its stages (ADR 0025) and each apply inside a stage reports or follows the run it finds.
- **Notifications.** A run nobody follows when it ends (no other process has its log open, 2 seconds after the end record, so a follower whose laptop went away has seen its last write fail) raises `apply-finished` (info) or `apply-failed` (urgent, with the error and the command that fixes it) through `events.Emit`, and sends it at once, when `notify.channels` are set up.
- **Status and doctor.** `keelbox status` shows a `setup` row while a run is running, or when the newest run died and no apply has been recorded since. Doctor reports the same as `logbook/setup-run`: ok while running, FAIL for a run that died, with the command that carries on; the scheduled doctor then sends `doctor-failed`.
- A run that has written its end record is over, though its unit lingers those 2 seconds: the next apply starts a new run instead of following it. The start waits up to 30 seconds for the apply lock, as apply does, since a day-two run may hold it shared for a moment.
- Before the first apply `/var/lib/keelbox` may be 0700 (made for the stage); the run makes it 0755, as the logbook module does, so an account in `sudo` reaches the log.
- The remote script removes the staged config at once and the staged secrets only while no `keelbox-apply-*` unit is active; the run removes them when it ends, so a `status` or `doctor` during a run does not take its Tailscale auth key away.

## Consequences
- Closing the laptop, a lost network or a killed keelbox does not cost the setup. A box that restarts mid-run still stops it; the next apply carries on.
- Over SSH, Ctrl-C is a question, not a stop.
- An account that starts a run with password sudo follows it without sudo through the `sudo` group. One not in that group cannot read the log: keelbox says so and leaves the run going, and `keelbox status` shows how it ended once the admin exists.
- Exit code 4 means keelbox stopped following a run that carries on.
- `keelbox up` on this machine (provider `local`) runs the apply as its own child under sudo: closing that window stops it after its step.
- Tested with a fake box for the follower (replay, Ctrl-C both ways, lost and regained connection, a run that died, report once), against the sim for the start and the run's end, and end to end on LXD: the laptop killed mid-apply and `up` continuing to Ready, SSH dropped for over a minute mid-apply, a concurrent apply attaching, a reboot mid-run reported as interrupted and carried on, and one notification for a run left running.

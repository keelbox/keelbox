# 0097: Apply keeps the SSH keys its last apply put on the box

Date: 2026-11-25. Status: accepted.

## Context
`keelbox up` wrote `ssh_authorized_key_files: [~/.ssh/id_ed25519.pub]` for both accounts. The file is read on the computer that runs keelbox, and apply replaces keelbox's marked block of each account's `authorized_keys` with what it reads. Copy the config to a second computer, add that computer's key, and apply from it: the block holds only the second computer's key, and the first computer is locked out of the admin and the agent, without a word. A simulated box showed it.

## Decision
- **Apply stops before taking a key off.** Before any change, apply compares the keys for the admin and the agent with the keys applies put there. Root keeps a record of them, `/etc/keelbox/ssh-keys.yaml`, with the sha256 of the config copy, `/etc/keelbox/keelbox.yaml`, there when it was written. The copy is written late in an apply, after `authorized_keys` changed, so the record says which of the two to trust. If the copy is the one the record saw, an apply since then stopped before writing its own, and the record holds what it may have put there; the copy's other keys are ones the user asked to come off. If the copy is another one, that apply got through and its keys are the record's, or a keelbox from before this change wrote it after a rollback and the record is stale: the copy, either way. With no record, on a box set up before it, the copy. The copy's key lists are read on their own so a change elsewhere in the schema cannot make the check pass by default. If a key would come off, it stops, exit 1, names each key by type, fingerprint and comment, names `keelbox apply BOX --remove-keys` for a computer no longer used, and ends with the YAML that keeps them and `keelbox apply BOX`: the last line is the safe one to copy. It runs ahead of the lock and of a detached run, as the container check does, so the refusal reaches the laptop at once.
- **The record is written before the steps.** Under the apply lock the check runs again, as another apply may have recorded a key since the first look, and then apply records its own keys before any step runs. Once the check has passed, every recorded key is in this config, or the user asked for the others to come off, so an apply that stops partway, after `authorized_keys` changed, leaves every key it may have put there in the record. With `--remove-keys` the keys taken off are not kept, so a step that fails later, before or after the copy, does not make every next apply stop or offer the key back. A record or copy that does not parse stops apply, naming the file; for the record, the message offers removing it, so the check reads the copy as on a box set up before it, and `--remove-keys` passes either.
- **Rollback leaves the keys as they are.** It applies the config the apply before left in `/etc/keelbox`. That config lacks a key a later apply added and then failed before copying its config, which is when rollback is most often run, and still lists a key a later `--remove-keys` apply took off. Under the apply lock, before anything changes, rollback sets that config's key lists to the keys applies put on the box, in a copy, `/var/lib/keelbox/stage/rollback.yaml`, has the older keelbox apply that, and lists each key it keeps or leaves off. Taking a key off, or putting one back, is apply's job; a rollback that did it could lock out the computer running it. `keelbox rollback BOX --remove-keys` applies the config as it is. The record then holds the keys handed over with the copy there now, so an older keelbox's apply that fails too leaves the record standing, and one that gets through is read from its own copy. A record or copy keelbox cannot read stops rollback. With `--remove-keys` the record takes the older config's keys before the older keelbox runs, so if that keelbox then refuses and changes nothing, a key a failed apply added is no longer tracked, as with an `apply --remove-keys` that fails before its first step.
- **The record is root's.** Only root can change it; the accounts' own `authorized_keys` is not read. The agent can edit its own, so a key it adds there cannot make apply stop.
- **A key is its type and data.** The same key with another comment is the same key.
- **`up` writes the key itself.** The config `keelbox up` writes lists the public key line under `ssh_authorized_keys`, so the config means the same on every computer. `ssh_authorized_key_files` still works and is read where keelbox runs.
- **Taking a key off is said aloud.** `--remove-keys` takes off keys the config no longer lists, for a lost laptop or a key taken out on purpose. Without it, a key taken out of the config also stops apply, every time until it is given.

## Consequences
- A second computer's apply can no longer lock the first one out. Taking a key off needs a flag.
- A box set up before this change has no record; its last applied config holds the keys read from the files of the computer that applied it, so the first apply from another computer stops and prints them as lines to keep.
- An apply by a keelbox from before this change, after a rollback, does not keep the record; once it copies its config, the check reads that copy, unless the copy is byte for byte the one the record saw, which takes such an apply putting back the config of the apply before the rollback; the record is then read. If it stops between `authorized_keys` and the copy, a key it added is in neither file; that keelbox cannot be changed.
- `keelbox init` still writes `ssh_authorized_key_files`; the check stops a second computer's apply of such a config.
- Not done: `keelbox export` and `import` of a box's config and host keys, and commands that add or remove a computer's key. The guide's steps are by hand for now.

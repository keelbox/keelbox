# 0076: The network limits apply to every account but root

Date: 2026-11-16. Status: accepted. Amends [ADR 0011](0011-agent-cannot-reach-admin.md). Builds on [ADR 0069](0069-agent-ssh-to-outside-addresses.md), [ADR 0070](0070-agent-net-subordinate-uids.md) and [ADR 0074](0074-agent-permissions.md).

## Context
The `inet keelbox_agent` table refuses two things: connections to the box's own SSH port (port 22 on the box's addresses, and the outside addresses of ADR 0069), and connections to link-local addresses, cloud metadata among them. Its first rule was `meta skuid != { the agent's uids } accept` (ADR 0070): the rejects applied to sockets the agent owns, and a socket of any other account passed.

With `users.agent.permissions: auto`, the default, the agent can have Ubuntu packages installed (ADR 0074). A package can bring a service that runs under an account of its own and connects where a local caller tells it: a forward proxy, a cache that fetches, a database with a command that reads from a remote source, a web server with a proxy module. That connection is made under the service's uid, which the table let through. So the agent could reach the metadata address, or the box's sshd, through such a service.

ADR 0074 put the proxies known to start that way on the deny-list of package names. A list of names cannot be complete: relaying is something many packages can do, not a kind of package. The same gap exists for a service root installs; with `auto` the agent can cause the install.

ADR 0070 rejected refusing by default and accepting known system accounts, because it puts every other account under the agent's limits. That cost is still there. It is now the smaller one.

## Decision
- **Both rejects apply to every uid but 0.** The rule for the box's own addresses, and the rule for each outside address on record, carry `meta skuid != 0`. Link-local destinations (`169.254.0.0/16`, `fe80::/10` and `fd00:ec2::254`, as before) go to a chain that ends in a reject for `meta skuid != 0`. A service under any account, installed by anyone, is refused there as the agent is.
- **Root keeps both.** cloud-init and the clouds' guest agents read the metadata service as root, and sshd, tailscaled and keelbox's own runs are root's.
- **The agent's uids come first at link-local addresses.** The chain's first rule refuses the agent's uid and its subordinate ranges (ADR 0070), before any exception. A uid of the agent's therefore never passes, whatever account name it also carries.
- **Fixed exceptions at link-local addresses, each one account and one kind of traffic.** They are the accounts Ubuntu's own packages create for the services a box needs from the link-local range on the supported clouds:

  | Account | Passes | Why |
  |---|---|---|
  | `systemd-resolve` | UDP and TCP port 53 | The resolver is `169.254.169.254` on Google Cloud and can be `169.254.169.253` on AWS; a router may announce its link-local IPv6 address as the resolver. |
  | `systemd-timesync`, `_chrony` | UDP port 123 | The time service is `169.254.169.123` on AWS and the metadata address on Google Cloud. |
  | `systemd-network` | UDP ports 67 and 547, ICMPv6 | A DHCP lease is renewed by UDP to the server that gave it, which is `169.254.169.254` on Google Cloud. A DHCPv6 server and an IPv6 router are reached at link-local addresses. |

  Each of these connects where its root-owned configuration or the network tells it, not where a local caller asks. The list is in the code (`linkLocalAccounts` in `internal/modules/agentnet.go`).
- **More accounts by config, for every port.** `host.firewall.link_local_accounts` is a list of account names that keep link-local addresses whole. It is for a machine where a service under its own account must read them, such as a cloud's monitoring agent on a machine keelbox adopted, and it is empty by default. The names are plain account names, at most 16. `root` is refused, since no rule limits it, and so is the agent account, since naming it would undo the limit. The key does not open the box's SSH port. It is under `host.firewall` because it is about what the box's packet rules let through, and it applies whether or not keelbox manages UFW. The config is the only source besides the code: it comes from the laptop, and its copy on the box is root's, so nothing the agent can write adds a name.
- **A named account is trusted as a relay.** If the agent can make that account's service connect where the agent says, the agent reaches the metadata service through it. keelbox cannot tell such a service from one that connects only where its own configuration says. The config reference and the security model say this where the key is described.
- **Resolved at apply, written as numbers.** apply looks each account up and writes its uid: the table loads before the network and must not depend on a name lookup then. An account the box does not have gets no rule, whether the code names it or the config does: apply does not fail for it, because a service may be installed after the box is set up, and doctor warns about a configured name that has no rule, with what to do. Neither does one whose uid is root's, or one of the agent's. The rules are sorted by uid, protocol and port, so the same box renders the same file.
- **Every reject carries the owner match.** A packet the kernel sends by itself (neighbour discovery to a link-local router, the answer to a ping, a TCP reset) has no socket that a process opened. nftables cannot evaluate `meta skuid` for it, so a rule with that match does not apply and the packet passes. The earlier table's rejects had no owner match of their own, and such a packet did not match the accept before them either, so as the rules read it refused the kernel's own packets to link-local addresses. That reading comes from the kernel's nftables source; neither table was observed doing it.
- **Doctor reads the loaded table by its parts**, since nft lists a rule its own way: port 22 at the box's own addresses, and every address on record, refused to every uid but root's; both link-local ranges sent to the chain; the uids refused first there exactly the agent's uid and its ranges in `/etc/subuid`; the exceptions exactly those of the accounts the box has now and of the configured names; every other uid but root's refused. An accept that is not one of the exceptions fails the check. A table without these rules fails it, and the finding ends with `keelbox apply BOX`. So does an account of the list that came or went since the last apply.
- **The same table, file and unit as ADR 0070.** Only the rules differ; apply validates the file with `nft --check` and loads the table again, as for any change to the rules.
- **The proxy deny-list stays**, as a second line: for a relay whose sockets are root's, and for a box whose table is not the one loaded.

## Rejected
- **A longer deny-list.** It names packages, not what they do.
- **Limiting only the accounts an agent's install creates.** A service can run under an account that was already there (`www-data`, `daemon`, `nobody`), and the limit would again depend on a list kept up by hand.
- **Excepting the service accounts for every port.** Each needs one port; the metadata service is on another.
- **Exceptions from a file on the box.** One more thing to protect there. The box's config already comes from the laptop and is root's on the box.
- **A port with each configured account.** What such a service reads is usually the metadata service itself, on the port the limit exists for, so a port would narrow little and ask the owner for something they may not know.
- **Failing apply for a configured name that is no account.** The service may come later, and a missing account opens nothing.
- **Refusing only connections the box opens** (`ct direction original`), so that a service under its own account could still answer a client that reaches it from a link-local address. The table does no connection tracking; a packet that tracking does not follow would have to be decided some other way; and the agent could then answer a link-local peer, which it cannot.

## Consequences
- **What an admin loses.** An account that is not root, the admin included, cannot open the box's own port 22 from the box (`ssh localhost`, or a tool that reaches the box through its own address) or query the metadata service. Both work with `sudo`.
- **A service under its own account that reads metadata stops getting it, unless its account is named in `host.firewall.link_local_accounts`.** A monitoring agent (DigitalOcean's runs as `do-agent`), an application that takes cloud credentials from the instance's role, a login helper that fetches keys from metadata (EC2 Instance Connect runs as `ec2-instance-connect`). The reject is immediate, so such a service fails rather than hangs. Boxes keelbox creates are not affected: on AWS they are Lightsail instances, on Google Cloud they have no service account, and keelbox enables no monitoring agent. A machine set up with `keelbox up` that already ran such a service is. These are named from the packages' documentation and were not tried.
- **No answer to link-local clients from a service that is not root's.** The rules look at each packet, not at who opened the connection. A service under its own account cannot answer a client that reaches it from a link-local address, such as a neighbour on the LAN that uses the box's `fe80::` address. sshd's connections are root's sockets and are not affected. Previews are served on tailnet addresses.
- **A box that resolves names without systemd-resolved's stub.** Where `/etc/resolv.conf` names only link-local resolvers, every account but root loses name resolution, apt's `_apt` included, so `apt-get update` fails. The agent already had none there. Ubuntu's images use the stub at `127.0.0.53`. Doctor reads the file (through its link, as the account that owns the directory it points into) and fails with the two ways out: systemd-resolved's stub, or the accounts that must resolve named in `host.firewall.link_local_accounts`, with which it warns instead, because the agent cannot be named and still resolves nothing. A file that also names a resolver elsewhere is left alone: the refusal is immediate and the C library goes on to the next. DNS over TLS (port 853) to a link-local resolver is not excepted either.
- **The impact report says so before the first apply.** `keelbox plan --impact`, and so `keelbox up` on a machine in use, states the rule once, with the key that keeps an account's access. It lists such a `resolv.conf` as an item the first apply stops for (ADR 0038), since the apply's own downloads would fail once the table is loaded. It also names each socket connected to a link-local address under an account that would lose it, from one look at the socket table (`ss`), with that account as the name to put in the key. That look is cheap and incomplete: a service that asks the metadata service once a minute is seen only if the look falls on a request. An empty list is not evidence that nothing uses those addresses, which is why the rule is stated whatever the look finds, and why those lines do not stop the apply. A new server, with nothing of an owner's on it, gets none of these lines.
- **An account of the list that appears later** (a package that brings chrony) has no rule until the next apply; doctor fails in that time, and its service cannot reach a link-local time source.
- **Still not covered:**
  - A socket root owns. A root service that connects where a local caller tells it (tailscaled's local API before Tailscale 1.98, in the security model) and a setuid-root program that opens a connection for its caller are outside the table.
  - Forwarded traffic. A container of the system Docker daemon or a virtual machine on a bridge is not output traffic and has no socket owner. The agent has no access to the system daemon.
  - The internet and the tailnet. A relay under any account reaches them, as the agent itself does; keelbox has no egress allowlist.
  - An address of the box keelbox was never told (ADR 0069).
- **What is tested.** Unit tests run the rendered rules for the agent's uid, a subordinate uid, another login account, a service account, each excepted account on and off its port, root and a packet with no owner, over IPv4 and IPv6. Tests against the simulated box cover doctor and an apply over the table ADR 0070 wrote. `nft --check` accepts the rendered file (nftables 1.1.6). On a local test VM the end-to-end test checks, as `nobody`, no connection to the box's port 22 or to the metadata address; as root, the box's port 22 on loopback; name resolution for the agent and for root, a time source that answers, and `apt-get update`. Root reaching the metadata address is checked only on the four clouds, where this test has not run, so each cloud's resolver and time source are from the vendors' documentation.

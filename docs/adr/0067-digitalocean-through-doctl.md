# 0067: DigitalOcean through the user's doctl

Date: 2026-11-12. Status: accepted. Supersedes the DigitalOcean line of [ADR 0027](0027-delegated-auth.md).

## Context
ADR 0027 recommended that a DigitalOcean provider sign in with DigitalOcean's OAuth as a public client and keep a refresh token in the credential store. keelbox's AWS provider runs the user's own AWS CLI ([ADR 0065](0065-aws-through-the-aws-cli.md)): keelbox holds no credential, adds no SDK and reads JSON. DigitalOcean's CLI, `doctl`, fits the same pattern, and since 2.x it does the OAuth sign-in itself (`doctl auth login`).

Facts the design relies on. Read 2026-11-12 in doctl v2.4.0 (source and the binary's own help), the DigitalOcean OpenAPI specification and docs.digitalocean.com; the commands, flags and JSON were also run through the doctl 2.4.0 binary against a stub of the API (`internal/provider/digitalocean/realcli_test.go`):
- **Sign-in.** `doctl auth init [--context NAME]` saves an API token; `doctl auth login` signs in through the browser (OAuth with PKCE) and stores a refresh token. Both write `config.yaml` in doctl's config directory, mode 600. `--context NAME` selects a saved context for one command. `DIGITALOCEAN_ACCESS_TOKEN` and `--access-token` apply to the default context only. Without a token, and for a context that does not exist, doctl says "access token is required".
- **Output.** With `--output json` a failed command prints `{"errors":[{"detail","title","reason","status"}]}` on standard output, nothing on standard error, and exits 1. Lists are followed across the API's pages by doctl itself. An error on a page after the first is dropped by doctl, which then prints a shorter list and exits 0.
- **Droplets.** `doctl compute droplet create NAME --region --size --image --tag-names a,b --user-data-file PATH [--ssh-keys ID]`. User data may be a `#cloud-config` document. Names are not unique. Status is `new`, `active`, `off` or `archive`; a create returns before the Droplet has an address. doctl's help: "If you do not specify any SSH keys, we email a temporary password to your account's email address"; a DigitalOcean support page says the password is not emailed. The API has no field to turn a root password off.
- **Tags** are single strings (letters, digits, `:`, `-`, `_`; at most 255 characters), not key and value. Creating a Droplet with tags creates the tags. A firewall can only name a tag that exists. Deleting a tag removes it from its resources. Nothing removes a tag no resource carries.
- **Cloud Firewalls** are free, apply to Droplet ids or to tags, and carry no labels of their own. "You can also tag a Droplet when you create it, which means you can apply firewall rules immediately." With no outbound rules, "no outbound traffic is permitted". Every port is `"0"` in the API's answers. An update replaces the whole firewall.
- **Address.** "The IPv4 and IPv6 addresses assigned to a Droplet remain static for the life of the Droplet. Once the Droplet is destroyed, the addresses are released back into a pool."
- **Tokens** can have custom scopes, one per API endpoint; a call outside them answers 403. A token without custom scopes reaches every resource of its team.
- **Price.** `price_monthly` is in US dollars. Droplets are billed per second up to a monthly cap, and "you are still billed for ... Droplets that are powered off".

## Decision
- **Provider `digitalocean` runs the user's installed doctl.** `internal/provider/digitalocean` executes `doctl ... --output json --interactive=false` and reads the JSON. keelbox holds no DigitalOcean credential and adds no SDK. The config names a doctl context (`target.digitalocean.context`, passed as `--context`), a region, a size and an image; the sign-in is whatever that context already has. There is nothing for `keelbox forget-token` to remove.
- **Why not OAuth in keelbox, as ADR 0027 proposed.** One pattern for every cloud that has a CLI: the same seam, fake and tests as AWS. No credential held: an OAuth client in keelbox would put a refresh token in keelbox's store, which is one more secret on the laptop and one more thing to rotate. No registration of keelbox as an OAuth client, at runtime or otherwise. And doctl offers the browser sign-in itself, so the short-lived, scoped token ADR 0027 wanted is available through it.
- **Two tags mark keelbox's Droplets.** The labels every cloud resource of keelbox's carries (`keelbox=true`, `keelbox-box=<box>`) become the tags `keelbox` and `keelbox-box-<box>`. `Find` and `Destroy` touch a Droplet only when it carries both and is named after the box. `target.digitalocean.tags` adds the user's own and cannot name either of keelbox's. `create` fails when any Droplet of the box's name exists, so names stay unique among keelbox's.
- **The firewall applies to the box's tag and exists first.** One Cloud Firewall per box, named `keelbox-<box>`, applied to the tag `keelbox-box-<box>`: inbound UDP 41641 always and TCP 22 until the box has closed public SSH ([ADR 0022](0022-hetzner-cloud-firewall.md)); outbound everything, which DigitalOcean needs written as rules. `create` makes the tag, then the firewall, then the Droplet with the tag, so the Droplet is never without it. Firewalls carry no labels, so keelbox knows its own by name and target: a firewall named `keelbox-<box>` that does not apply to the box's tag is not touched, and stops the command. An update passes back the firewall's tags and Droplet ids, because an update replaces everything.
- **First contact is verified, and the first login is the admin.** The host key is generated on the laptop, pinned before the Droplet exists and installed by cloud-init, as on Hetzner (ADR 0007); `RotateHostKeys` replaces it after the first verified connection. The user data is a cloud-config (`provider.AdminUserData`) that creates the admin account with the user's keys and passwordless sudo, and sets `ssh_pwauth: false` and `disable_root: true`. It goes to doctl as `--user-data-file`, a mode 600 temporary file removed afterwards, never as an argument. Two other ways in were rejected: root with an SSH key stored in the DigitalOcean account leaves a key in the account that keelbox would have to create and delete; root with keys from the cloud-config keeps a root login open until the first apply. This way nothing is added to the account and root never takes an SSH login.
- **No account key is added; one that is already there is used.** When the account holds an SSH key that is one of the admin's (compared by key, not by name), `create` names it with `--ssh-keys`, so DigitalOcean sets no root password. A token that may not list keys is not an error.
- **No Reserved IP.** A Droplet keeps its public IPv4 address for its life, a power off and on included, so there is nothing to allocate, attach or release.
- **Destroy leaves nothing.** It deletes the Droplet, waits until it is gone, deletes the firewall, then deletes the tags `keelbox-box-<box>` and `keelbox` when no resource carries them. With no Droplet, `destroy` still removes a firewall and tag an interrupted `create` left.
- **Preflight names the fix.** No doctl on PATH: the install page. No token for the context: `doctl auth init`, with `--context` filled in. A token the API refuses: the same. A token without the `account:read` scope: the scopes keelbox needs. A region that takes no new Droplets: those that do. A size or image not offered in the region: some that are.
- `keelbox up` offers DigitalOcean, checks the sign-in, and lists the regions and the sizes that can be ordered there, with the monthly prices doctl returns. Without a terminal the region must be given: doctl has no default region to fall back on.

## What the credential can reach, and what is checked
- doctl's token can do whatever it is allowed in the whole team; keelbox cannot narrow it. keelbox itself runs `account get`, the region, size and image lists, `ssh-key list`, and creates, reads, updates and deletes only Droplets, firewalls and tags, and of those only the box's tagged Droplet, its firewall and keelbox's two tags. That is enforced by keelbox's own code and covered by tests against a fake doctl (`TestNeverTouchesDropletsOrFirewallsItDidNotMake`), not by DigitalOcean.
- To have DigitalOcean enforce the kinds of resource, give keelbox a doctl context with a custom-scoped token: `account:read`, `regions:read`, `sizes:read`, `image:read`, `droplet:create`, `droplet:read`, `droplet:delete`, `firewall:create`, `firewall:read`, `firewall:update`, `firewall:delete`, `tag:create`, `tag:read`, `tag:delete`, and optionally `ssh_key:read`. Scopes do not limit by tag: such a token still reaches every Droplet and firewall of the team.
- The host key never reaches a command line: a test fake fails if it appears in an argument and checks the file's mode, and the contract test checks that the real doctl reads the file.

## Consequences
- DigitalOcean needs doctl on the laptop. Without it `keelbox up` says how to install it and stops (exit 3 without a terminal).
- A command that reaches DigitalOcean costs one `account get` more than it strictly needs, so that a missing or refused token is reported with its fix.
- When the account holds none of the admin's keys, DigitalOcean sets a root password for the Droplet and may email it to the account. SSH never accepts it: passwords and root login are off from the first boot. It works only at the Droplet console in the control panel, behind the DigitalOcean sign-in. DigitalOcean's documents do not settle whether the email is sent, or whether user data changes that.
- Tested against the fake, with the real doctl against a stub API, and end to end on a real account (`make e2e-digitalocean`).
- A partial list from doctl (an error on a later page) could hide a Droplet from `Find`. It errs towards "no Droplet named ...", never towards touching the wrong one.
- Prices are in US dollars before tax. `up` lists only sizes that can be ordered in the chosen region, and a short list of the cheapest; `--size` takes any.
- IPv6 is not enabled on the Droplet: keelbox connects over IPv4.

# 0027: Delegated sign-in for cloud providers

Date: 2026-11-06. Status: accepted. The DigitalOcean point is superseded by [ADR 0067](0067-digitalocean-through-doctl.md) and the AWS point by [ADR 0065](0065-aws-through-the-aws-cli.md).

## Context
Pasting a long-lived API token is the step new users find hardest and the credential with the widest reach on their laptop (ADR 0026). Many CLIs instead open a browser and get a short-lived, scoped token through OAuth. The question: which providers let a distributed open-source CLI do that as a public client, with no client secret and no hosted backend of keelbox's own? RFC 8252 section 8.5: secrets "statically included as part of an app distributed to multiple users should not be treated as confidential secrets", and the server "MUST treat the client as a public client". RFC 8628 section 5.6 says the same of device-flow clients.

## Findings (read 2026-11-06)
- **Hetzner Cloud: no delegated auth.** The API reference ([docs.hetzner.cloud](https://docs.hetzner.cloud/), changelog to 2026-11-02) says "All requests to the Hetzner Cloud API must be authenticated via a API token" and "A token is bound to a Project". Tokens are created in "Hetzner Console (https://console.hetzner.com/) choose a Project, go to Security → API Tokens". Permissions are Read or Read & Write only ([generating an API token](https://docs.hetzner.com/cloud/api/getting-started/generating-api-token), 2021-12-13); no expiry is documented. No OAuth, OIDC, device flow or app marketplace appears in the reference or changelog (an absence, so inferred, but from the full reference). The Cloud Console moved to console.hetzner.com on 2025-06-25 ("the new Hetzner Console (formerly Cloud Console)"); `console.hetzner.cloud/projects/<id>/security/tokens` redirects to `console.hetzner.com/projects/<id>/security/tokens`.
- **DigitalOcean: public clients supported.** [OAuth API](https://docs.digitalocean.com/reference/api/oauth/), verified 2026-10-20: "Public clients cannot securely store a client secret, such as native, desktop, command-line ... They have no client secret and instead secure the authorization code exchange using PKCE." Clients register at runtime with an unauthenticated POST to `/v1/oauth/register`; loopback redirect URIs match on any port; S256 only; access tokens last an hour with single-use refresh tokens. Scopes are fine-grained (`droplet:create`, [scopes](https://docs.digitalocean.com/reference/api/scopes/), 2026-11-06). `doctl auth login` signs in through the browser.
- **Linode / Akamai: public clients, implicit flow only.** [API get started](https://techdocs.akamai.com/linode-api/reference/get-started), 2026-08-21: clients can be made public, and use the implicit flow; the token "expires in two hours. No refresh_token is issued." No PKCE or device flow is documented. linode-cli embeds a public client ID, takes the token on a localhost redirect, then creates a non-expiring personal token with it (`linodecli/configuration/auth.py`, 2026-09-18).
- **AWS IAM Identity Center: runtime public-client registration.** [RegisterClient](https://docs.aws.amazon.com/singlesignon/latest/OIDCAPIReference/API_RegisterClient.html): "Registers a public client with IAM Identity Center ... authorization code grant with ... PKCE or the device code grant"; `clientType` "supports only public". The per-registration secret is generated at runtime, and the OIDC calls need no AWS credentials. The user needs Identity Center enabled and a permission set; the result is short-lived role credentials. AWS documents the flow for the AWS CLI; third-party use works but is not presented as a product.
- **Others.** Vultr: API keys with an IP allow-list ([docs](https://docs.vultr.com/platform/other/api/enable-user-api-access)). Scaleway: access and secret keys ([IAM](https://www.scaleway.com/en/docs/iam/concepts/)). OVHcloud: requests are signed with an application secret, so not a public client ([first steps](https://docs.ovhcloud.com/en/guides/manage-and-operate/api/first-steps), 2025-05-13). Google: desktop apps are public clients with PKCE and a loopback redirect ([native apps](https://developers.google.com/identity/protocols/oauth2/native-app)); the device flow cannot request `cloud-platform`. Microsoft Entra: device code grant without a secret ([device code](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code), 2026-06-15).

## Decision
- Hetzner stays on project tokens: there is nothing else. keelbox makes the token step as short as it can (ADR 0026): it links the console, recommends a project used only for keelbox (a token reaches every server in its project and nothing outside it), asks for Read & Write, checks the token, stores it in the OS credential store, and treats it as non-expiring, with `keelbox forget-token` and a pointer to revoke it in the console.
- DigitalOcean: sign in with DigitalOcean OAuth as a public client: dynamic registration, PKCE, a loopback redirect, the narrowest scopes create, apply and destroy need, the refresh token in the credential store. No hosted secret, so no keelbox service to run. (Superseded: ADR 0067 runs the user's doctl, which does this sign-in itself.)
- AWS: Identity Center's device or PKCE flow and short-lived role credentials, never access keys. (Superseded: ADR 0065 runs the user's AWS CLI.)
- keelbox has no Linode provider. Linode's implicit flow gives a two-hour token without refresh, and converting it into a non-expiring token, as linode-cli does, would bring back the long-lived secret.

## Consequences
- The first Hetzner box needs one visit to the Hetzner Console. The wizard cannot remove that step.

# 0071: Resize, park and resume a cloud box

Date: 2026-11-14. Status: accepted.

## Context
A box on a cloud is billed for as long as its server exists. There are two things an owner wants to do with a box that works:

- Change the server's size, when an agent needs more memory for a while or the box turned out larger than its work.
- Stop paying for the server during a pause of weeks, and have the same box back afterwards.

Switching a server off does not stop its bill on any of the four clouds keelbox creates servers on. On Hetzner, AWS (Lightsail) and DigitalOcean a server that is switched off costs what a running one costs. On Google Cloud a stopped VM's disk and its reserved address stay billed. So the server has to be deleted, and what can be kept cheaply is a snapshot of its disk. On Hetzner the round trip is quick: shutting a server down, taking a snapshot and deleting the server takes 40 to 48 seconds on a small disk, and a server created from the snapshot answers SSH after 30 to 60 seconds. Files, Docker's images and volumes, systemd units and the nftables rules come back as they were. Two things do not, unless the create call says so: cloud-init runs again on the new server and by default deletes and regenerates the SSH host keys, and a firewall attached after creation leaves the server without it for its first seconds.

The clouds differ in what they let a caller do about each of these:

- **Size.** Hetzner, DigitalOcean and Google Cloud change the size of a stopped server in place and can leave its disk alone. Lightsail cannot change an instance's plan, and creates an instance from a snapshot only on a plan at least as large as the one the snapshot came from. A Lightsail instance's name cannot change either.
- **User data.** Hetzner, DigitalOcean and Google Cloud hand a cloud-config document to cloud-init before it touches the host keys. Lightsail's user data is a shell script, which runs after cloud-init has already made new host keys on a new instance.
- **The default account.** An image's own cloud-init configuration may name an account to create on a new server. On Google Cloud that is `ubuntu` with passwordless sudo, which a box created by keelbox never had. DigitalOcean's configuration for every new Droplet turns SSH passwords and root's keys on.
- **The firewall.** Hetzner takes the firewall in the call that creates the server. Google Cloud's rules apply to a network tag the VM is created with. DigitalOcean has no firewall parameter at creation and applies a Cloud Firewall only after the Droplet is active. Lightsail opens ports 22 and 80 on every new instance and takes other rules only for an instance that exists.
- **What is billed without a server.** A snapshot, everywhere. On Lightsail also a static IP attached to nothing; on Google Cloud also a disk and a reserved address nothing uses.
- **Prices.** Hetzner's API reports the price of snapshot storage. The Lightsail and DigitalOcean APIs do not, and gcloud reports no prices at all.

## Decision

**Three commands, run by the owner.** `keelbox resize BOX`, `keelbox park BOX` and `keelbox resume BOX`, on Hetzner, AWS (Lightsail), DigitalOcean and Google Cloud. They exist for boxes whose server keelbox created on a cloud; on a box of provider `ssh` or `local` they say there is nothing for them to do. Nothing parks or resizes a box by itself.

**Resize keeps what is on the disk, and the disk's size wherever the cloud allows.** resize lists the sizes the server can change to with the cloud's prices where it gives them, as `keelbox up` lists sizes, marks the current one and asks; without a terminal it needs `--size`, and stops before any change without it (exit 2, the convention of [ADR 0025](0025-keelbox-up.md)). Before the go-ahead it says that the box restarts and that running sessions stop. Then it shuts the server down through its operating system, changes the size, starts the server, waits for SSH and runs the normal apply. Where the cloud can change a server back down, only sizes that leave that possible are listed, and the disk keeps the size it was created with, because a disk that has grown cannot shrink. The size key of the box's config is rewritten in place, one value on one line, so the file's comments stay; a file not written as block mappings is left alone and the line to set is printed.

**Park is shut down, snapshot, confirm, delete, in that order.** park says what happens and what stays billed, with the price of snapshot storage where keelbox has one, and asks, No by default. Then: a shutdown through the operating system; a snapshot of the disk; a wait until the cloud reports the snapshot complete and usable; and only then the deletion of the server. If any step before the deletion fails, the server is started again and park says so. No code path deletes a server whose snapshot the cloud has not confirmed. Whatever the cloud bills without a server, apart from the snapshot, is given up with the server: the public address everywhere, and with it Lightsail's static IP and Google Cloud's disk and reserved address. The cloud's firewall for the box is kept where it exists apart from the server, with its rules, for the server resume creates.

**The parked state lives in the cloud.** The snapshot carries the box's labels and a parked marker: `keelbox=true`, `keelbox-box=<box>`, `keelbox-parked=true` (tags on Lightsail; on DigitalOcean, whose tags are single strings, `keelbox`, `keelbox-box-<box>` and `keelbox-parked`). A box with no server and such a snapshot is parked, whichever computer asks. The laptop keeps a note beside the box's config (`boxes/<box>.parked.json`: the date, the address the box had) only so that `keelbox ls` and `keelbox status --all` can say "parked" without a call to the cloud, and so that resume knows which pinned host keys to move. The note is never the authority: a command that finds a server deletes it, a command that finds the snapshot writes it.

**Every other command says parked and names the fix.** Commands that connect to a cloud box all find its server first. When there is none and a parked snapshot exists, they stop with one line: the box is parked since the date, and `keelbox resume BOX`. `keelbox up` and `keelbox create` do the same before they would create a server, so a parked box never gets a second, empty one. park on a parked box and resume on a running one say so and exit 0; resume on a box that is not parked whose server is off starts it, which is the way back when a park or resize could not start the server again.

**Resume creates the server from the snapshot and applies.** The new server has the box's name and the size, location and labels of the config, the box's firewall, and no login the disk does not have. cloud-init is told to keep the SSH host keys and the hostname on the disk and to create no account (`ssh_deletekeys: false`, `preserve_hostname: true`, `users: []`) and nothing else. The host keys are therefore the ones the laptop already pinned, and resume pins them under the new address ([ADR 0007](0007-host-key-pinning.md): nothing new is trusted). It then waits for SSH and runs the normal apply as the admin, because cloud-init on a new server may undo what an earlier apply did, such as locking the image's default account. The snapshot is deleted only after that apply passed. When the apply fails the snapshot stays, and resume run again carries on with the server that exists.

**No default account on a resumed server.** The empty `users` list is part of what resume tells cloud-init on every cloud. Without it the image's cloud-init configuration decides, and on Google Cloud it creates `ubuntu` with passwordless sudo on the new VM. The end-to-end test compares the accounts, their password states, the sudo rules and the authorised keys before a park and after the resume.

**Destroy covers parked boxes.** `keelbox destroy` on a parked box deletes the snapshot and what create made besides the server. The check for work that exists only on the box ([ADR 0064](0064-work-on-the-box.md)) cannot run without a server, so destroy says that the snapshot holds everything that was on the box and asks as it does for a server that does not answer; `--yes` does not answer that question. A destroy of a box with a server also deletes a parked snapshot left beside it. As everywhere, only resources labelled `keelbox=true` for the box are touched.

**One interface, the order in shared code.** The `cloud` interface in `internal/cli/cloud.go` gains the calls a provider must supply: `sizeKey`, `sizes`, `stop`, `start`, `resize`, `parkCost`, `snapshot`, `release`, `parked`, `restore` and `discard`. The commands in `internal/cli` own the order of the calls, the questions, the messages and the laptop's note; a provider owns only the calls to its cloud. The rule that matters most, no deletion before a confirmed snapshot, is therefore written and tested once. All four clouds implement the calls. Three things a cloud may need beyond them are optional and also handled once in the shared code: a file that must be on the box before its disk boots on another server (`hostKeyKeeper`), a line resize must say before the go-ahead (`resizeWarner`), and a resize that ends with the box parked (`errLeftParked`).

**The security model says what a snapshot is.** A snapshot is the whole disk, with the agent's sign-ins and every secret file on the box, readable by whoever can read snapshots in the cloud account. keelbox adds no encryption to it. `docs/security-model.md` says so and lists it among the owner's responsibilities, with the windows listed under Consequences.

### Hetzner

The change of size is `change_type` with `upgrade_disk: false`, and only types of the same architecture whose disk is at least the server's disk are offered. The size key is `target.hetzner.server_type`. At resume the Cloud Firewall is named in the create call, so the server never runs without it, and the call names the project SSH keys of the config, as create does: Hetzner otherwise sets a root password and mails it.

### AWS (Lightsail)

**Resize replaces the instance, under the same name and address.** Lightsail has no call that changes a plan. resize takes a snapshot of the stopped instance, waits until Lightsail reports it available, deletes the instance, creates an instance of the same name from the snapshot on the larger plan, gives it the firewall rules the old one had and attaches the box's static IP, then deletes the snapshot. The name is kept because keelbox finds a box's instance by it and Lightsail cannot rename one. The static IP is never released during a resize, so the address is kept. Only the current plan and plans at least as large in disk, memory and vCPUs are listed, because Lightsail creates nothing from a snapshot on a smaller plan: the disk grows to the new plan's size and the box cannot be made smaller again. resize says so before the go-ahead, and as a note with `--yes`.

**The resize snapshot is marked parked before the instance is deleted.** From the deletion until an instance exists again, the box is its snapshot. With the parked marker on it, that state is one keelbox already knows: an interrupted resize is a parked box, and `keelbox resume` brings it back, whatever happened to the process that started the resize. If the instance cannot be created on the larger plan, resize creates it again on the old one; if that fails too, it leaves the box parked with its static IP kept and says so. An interrupted resize therefore needs no recovery path of its own.

**A cloud-init file on the disk, and a check for it.** Lightsail's user data runs too late to keep the host keys, so the disk has to say so itself. apply keeps `/etc/cloud/cloud.cfg.d/99-keelbox.cfg`, with the three settings above, on any machine cloud-init identifies as AWS. A box without it would come back from a resize or a resume with host keys the laptop refuses, so `keelbox resize` and `keelbox park` check over SSH that the file is there and stop before any change if it is not, with `keelbox apply BOX` as the fix. The instance resume creates gets a launch script that does nothing, and no key pair is named.

**Park releases the static IP.** Lightsail bills one that is attached to nothing. An instance's firewall is part of the instance, so park records on the snapshot whether it admitted SSH and resume sets the box's rules accordingly; a resize copies the old instance's rules to the new one. The size key is `target.aws.bundle`; the plan at resume must be at least as large as the one the snapshot was taken on.

### DigitalOcean

**Resize changes vCPUs and memory only.** The disk keeps its size (no `--resize-disk`), so every size listed can be changed back from; the sizes listed are the ones orderable in the Droplet's region whose disk is at least the Droplet's. The size key is `target.digitalocean.size`.

**At resume the Droplet is named in the firewall by id, and resume waits.** The box's Cloud Firewall applies to the box's tag and is kept while the box is parked. DigitalOcean applies it to a new Droplet only after the Droplet is active, and for a firewall that names a tag it first has to find the Droplet by that tag. A Droplet created from a snapshot boots with everything on its disk listening, so resume adds the new Droplet to the firewall by its id straight after the create call, keeps the tag as well, and returns only when DigitalOcean reports the firewall applied to it. Over 8 runs, a Droplet that carried only the tag answered on port 22 before the firewall took effect in 2, for about 2 and about 32 seconds; a Droplet also named by id, in none of 8.

**The snapshot is tagged after it starts.** DigitalOcean takes no tags in the call that starts a snapshot. keelbox finds the new snapshot in the list and tags it, about a second later, before it waits for it. The snapshot's name, `keelbox-parked-<box>`, is for the control panel; keelbox knows the snapshot by its tags.

**Root and passwords as at create.** resume names one of the admin's SSH keys when the DigitalOcean account holds it, as create does, because DigitalOcean otherwise sets a root password on the new Droplet. Its user data also sets `ssh_pwauth: false` and `disable_root: true`, the two settings create uses, so that cloud-init on the new Droplet writes what the disk already says.

### Google Cloud

**Resize changes the machine type of the stopped VM.** The disk and the reserved address are not touched, so it works in both directions. The types listed are the ones `keelbox up` offers and, for a VM of another family, that family up to twice the VM's vCPUs. The size key is `target.gcp.machine_type`.

**Park is a snapshot of the boot disk, then the VM, its disk and its address go.** Google Cloud bills a disk without a VM and a reserved address nothing uses, and a parked box is to cost its snapshot only. So park deletes the VM with its boot disk and releases the address, after Google reports the snapshot `READY`. The two firewall rules stay; they cost nothing and apply to the box's network tag. park refuses, before the question, a VM with a disk attached beside its boot disk, because it would keep only the boot disk. If the address cannot be released after the VM is gone, park finishes with a warning and the command that releases it, and resume uses the address again.

**Resume reserves a new address and creates the VM from the snapshot.** The VM gets the machine type, zone, labels and network tag of the config, a `pd-balanced` boot disk at the size it had, and the login settings of a created box: project SSH keys blocked, OS Login off, no key in the metadata, no service account. The rules apply to the network tag, so they are in force from the moment the VM exists. If the VM cannot be created, the snapshot is kept and the address resume reserved is released again.

## Rejected
- **Parking automatically**, when a box has been idle for some time or on a schedule. An idle-looking box may hold a session waiting for its owner, a long test run or a dev server someone has open, and keelbox cannot tell. Parking stops all of it and changes the box's address. It also needs the cloud credential somewhere that acts without the owner, which keelbox avoids. The owner knows when a pause starts; one command is not much to ask.
- **Keeping the public address.** Hetzner can keep a primary IP without a server, Lightsail a static IP and Google Cloud a reserved address, and each is billed while kept. The saving is the point of parking, the tailnet name does not change, and keelbox's own records follow the new address at resume. An owner who needs a fixed address for something else can reserve one outside keelbox.
- **Keeping the parked state only on the laptop.** A lost or second laptop would then see a box with no server and offer to create one, and a snapshot nobody remembers would be billed for ever. Labels on the snapshot cost nothing and are where the snapshot is.
- **Stopping the server instead of deleting it.** On Hetzner, Lightsail and DigitalOcean it saves nothing. On Google Cloud the disk and the address are still billed, and one meaning of "parked" for every cloud is easier to explain.
- **Growing the disk with the type.** It makes the bigger type's disk usable and makes the way back impossible. An owner who needs a bigger disk for good creates a bigger box. Lightsail leaves no choice: there the disk grows, and resize says so first.
- **Leaving the host keys to cloud-init.** The new server would present keys nobody has seen, and resume would have to trust them on first use or inject a fresh single-use key as create does. Keeping the disk's own keys needs one line of user data, or one file on the disk on AWS, and trusts nothing new.
- **Deleting the snapshot as soon as the server runs.** A server that boots is not necessarily a box that works. Until an apply has passed, the snapshot is the only copy known to be good.
- **Putting the whole park in one provider call.** Each cloud would then order shutdown, snapshot and deletion itself, and the guarantee that matters would be implemented four times.
- **Leaving DigitalOcean's firewall to the tag at resume.** It is what create does, and at create a new Droplet listens on SSH only. A resumed Droplet starts everything on its disk, and with the tag alone the firewall was measurably late.

## Consequences
- A parked box costs its snapshot's storage and nothing else. On Hetzner the API reported EUR 0.0143 per GB a month in November 2026, and the snapshot of a freshly set-up box was 2.5 GB. DigitalOcean's published price was USD 0.06 per GB a month, which keelbox holds as a constant because the API gives none, on the size the snapshot reports: 6.7 GB for a fresh box. Google Cloud bills what the snapshot stores, 2.6 GB of a 20 GB disk for a fresh box, and keelbox states no price. Lightsail bills the snapshot by the disk's size, USD 0.05 per GB a month by AWS's price list, and keelbox prints no number.
- The public address changes at resume. Anything outside keelbox that pointed at the old one needs the new one.
- A box that had closed public SSH ([ADR 0021](0021-close-public-ssh.md)) comes back reachable over the tailnet only. If its Tailscale key expired while it was parked it cannot rejoin by itself, and the way in is the cloud's rescue console ([closing public SSH](../guides/public-ssh.md)). park says so before it asks, when it reads on the box that public SSH is closed.
- The size at resume is the config's. A config whose size was not rewritten after a resize, because the file could not be edited and the owner did not set the line, resumes at the old size. On Google Cloud `target.gcp.disk_gb` is not applied at resume: the disk has the size it had.
- A box on AWS can only grow, and each resize there creates a new instance.
- **The cloud's firewall is not in force from the first second on DigitalOcean and Lightsail.** On DigitalOcean, at resume, it applies some seconds after the new Droplet is active; resume returns only once DigitalOcean reports it applied. On Lightsail, at resume and at every resize, the new instance has Lightsail's default ports (22 and 80) open until Lightsail accepts the box's rules, which keelbox sends from straight after the create call and then reads back; how long that lasts has not been measured. During those seconds the box's own UFW (deny incoming by default, started before the network) and sshd's settings, both on the disk, are what applies.
- **[ADR 0067](0067-digitalocean-through-doctl.md) is not accurate on one point.** It says that because the tag and the firewall exist before the Droplet, the Droplet is never without the firewall. DigitalOcean applies a Cloud Firewall some seconds after a Droplet is active, also at create. At create that leaves a new Droplet answering only on what its image listens on, SSH, which a new box's firewall admits as well.
- **The agent's SSH rule lags by one apply on AWS and Google Cloud.** There the public address is translated outside the machine, so the box knows it only from `/etc/keelbox/outside-addresses` ([ADR 0069](0069-agent-ssh-to-outside-addresses.md)). From the boot of a resumed server until the apply at the end of resume, about a minute, the rule that rejects the agent's connections to the box's own SSH port still lists the old public address. The agent's lingering services and containers with a restart policy start at boot. sshd still asks for the admin's key, which the agent does not have. The apply records the new address.
- **A snapshot can be left untagged on DigitalOcean.** If keelbox is killed in the second between the start of a snapshot and its tagging, a snapshot named `keelbox-parked-<box>` without keelbox's tags is left. keelbox neither finds nor deletes it; the owner deletes it in the control panel.
- On DigitalOcean, when the account holds none of the admin's SSH keys, DigitalOcean sets a new root password on the resumed Droplet and emails it, as at create. It is expired and usable only at the console in the control panel; sshd refuses root and passwords.
- A server that ignores the shutdown is switched off by the cloud or by keelbox. On Hetzner and Lightsail keelbox forces the stop after 5 minutes. On DigitalOcean the stop then takes about 10 minutes, and keelbox says so at the 5 minute mark. Google Cloud switches the VM off itself and does not report it, so keelbox notes when a stop took 2 minutes or more.
- The commands need more of a restricted sign-in. A DigitalOcean token with custom scopes also needs `droplet:update`, `image:create`, `image:update` and `image:delete`; a restricted AWS profile needs the Lightsail snapshot, stop and start actions. `docs/guides/credentials.md` lists them.
- `keelbox up` on a box another computer parked relies on the cloud's answer when it is about to create a server; when its own record says the box is ready it prints that without asking the cloud. The next command that connects says the box is parked.
- A snapshot is not a backup: it is deleted at resume, and it is in the same account as the server was. Backups stay what [ADR 0020](0020-backups.md) describes.
- The end-to-end test `TestResizeParkResume` takes one box through resize up and down, park, resume, a second park and destroy on a live cloud, and checks the agent's files, a Docker volume, the host key fingerprint, the accounts and authorised keys, the feature and isolation checks, and what the cloud holds after each step. On AWS the resize down is replaced by a check that the smaller size is refused. It runs for a target that implements the harness's `parker` interface, which all four cloud targets do. It has passed on live accounts on all four clouds.

# 0064: Work that exists only on the box

Date: 2026-11-10. Status: accepted. Builds on ADR 0014 (sign-in), ADR 0041 (the status snapshot) and ADR 0056 (plain text).

## Context
Agents build projects in `/home/agent/projects` on a box that may be rented by the hour. Without a git identity nothing gets committed; without a check nothing says that a project is not in git or on any remote; and `keelbox destroy` with only a typed name deletes the only copy. Goal: nobody loses work on a box without being told.

## Decision
- **A git identity in the config.** `users.agent.git: {name, email}`, both or neither. `keelbox up` asks for it after the GitHub CLI question, offering this computer's `git config user.name` and `user.email`; another can be typed, or it can be skipped. `--git-name` and `--git-email` answer it. Without a terminal and without the flags it stays unset: keelbox does not put a person's name on a machine unasked.
- **Written with git, as the agent.** Apply runs `git config --global user.name` and `user.email` as the agent, and `init.defaultBranch main` only when no config git reads for the agent sets one. We chose this over an included file keelbox owns: an include needs a line in `~/.gitconfig` all the same, hides the values from `git config --global --list` readers who look in the file, and gives nothing back, since the agent can override either. git decides which file holds the keys and every other setting stays. The config is the source: an identity changed on the box is put back by the next apply. Without `users.agent.git` there are no steps and nothing is written.
- **Doctor says when there is none.** `runtime/git-identity` warns "no git identity: commits will fail" with the YAML to add, whoever was meant to set it; an identity the agent set itself is ok.
- **One probe for the projects.** `internal/projects` runs one shell script as the agent over each directory directly under the projects directory (`Config.ProjectsDir`: Remote Control's directory, default `projects`, the one the primer names). For each: is there a `.git`; `git status --porcelain` (changed and untracked paths); `git remote`; `git rev-list --count HEAD --branches --not --remotes` (commits no remote-tracking ref has). No fetch, so no network and no credentials: "not pushed" is as true as the last fetch or push. As the agent, never as root: names, git config and hooks there are the agent's to write, so git gets the agent's rights and its `safe.directory` check passes without an exception. Symlinks in the directory are not followed and hidden directories are not projects. Each repository has 3 seconds and the probe 8 in git, then 30 in all; a repository that does not answer in time is "could not be checked" and counts as work that may be only here. At most 50 directories are read; the rest are counted. Names come back hex-encoded, are made one plain line (ADR 0056) and cut to 40 characters.
- **Where it shows.** `keelbox status BOX` reads the probe live and prints a `projects` row and a line a project, work that is only on the box first, ten at most, then "and N more". The watch run puts the same in the status snapshot (`projects`), which the agent's own sudo-less `keelbox status` prints. `keelbox status BOX --json` prints a snapshot collected now.
- **Doctor warns once.** `runtime/projects`: a warning, never a failure, with counts by state and the command that lists them. No project names: scheduled doctor findings become notifications, and a name is the agent's text. It is marked flaky, so with `doctor.notify_warnings` it alerts after two runs in a row, not each time an agent has uncommitted work.
- **destroy asks.** Before deleting a Hetzner server, `keelbox destroy` reads `status --json` from the box. If any project is not a repository, has uncommitted changes, commits not pushed, no remote, could not be checked or was not read, it lists them (plain, ten at most) and asks `Delete this work with the server? [y/N]`. If the box does not answer within 2 minutes it says it could not check and asks `Delete it without knowing? [y/N]`. Without a terminal it deletes nothing, exits 1 and names `--discard-work`, which skips the check. `--yes` keeps its one meaning, no typing of the box name; it never answers the question about the work. The typed-name confirmation comes after.
- **The primer and Ready.** The primer has a section "Your work": what is not pushed exists only on this box; start projects with `git init` and a `.gitignore`; commit as you go; ask where to push; `keelbox status` lists what is not committed or pushed. The Ready card's line for a skipped GitHub sign-in says what that means: the agent's work stays on the box unless it is pushed another way or copied off.

## Consequences
- The check is against accidents, not against the agent. It reads the agent's own repositories with the agent's git: an agent can make a project look pushed. It sees only directories directly under the projects directory, and only git: work elsewhere in the home, stashes, files a `.gitignore` leaves out, a database in a container volume and a remote that is another directory on the same box are all invisible to it. The guide says so.
- The status snapshot, world-readable on the box, holds the names of the agent's project directories.
- The watch run does a little git every two minutes. One `timeout` per repository, because `timeout` itself takes a tenth of a second on Ubuntu's newer coreutils; a box with 50 repositories spends about 5 seconds there.
- git may still accept a commit without an identity on a machine whose host name is fully qualified, by guessing an address. Doctor's warning says commits will fail, which is what a cloud server does.
- The destroy question tells the owner to push or copy; how is theirs.
- Tested against real git for the script (each state, a hanging hook, hostile names, a symlink out), against the fake Hetzner API for destroy, and on an LXD VM for status, the agent's status, doctor and the JSON destroy reads.

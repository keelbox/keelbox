# 0095: A cloud's refusal to create a server leaves nothing behind and offers the ways on

Date: 2026-11-25. Status: accepted. Amends ADR 0025 (keelbox up) and ADR 0035 (answers kept).

## Context
Since June 2026 Hetzner limits new cloud servers for new customers and for some existing ones, per location, citing limited hardware. An affected account cannot create or rescale servers in that location. Hetzner does not document the API's error for it. Reports name `resource_unavailable` (412) for a type out of stock, `resource_limit_exceeded` (403) for a project limit and `placement_error` (422); none of that is verified. keelbox printed the API error as it came, with no fix. The firewall `create` had made stayed behind. `keelbox up` had written the box's config by then, so it ignored `--location`, `--size` and `--provider` on the next run: the only way to another cloud was `keelbox forget`, then every question again.

## Decision
- **A refusal is a 403, 412 or 422 from the order** (create, resume, change type) that is not about keelbox's own request or token: the three codes above, `forbidden`, and any code keelbox does not know. `invalid_input`, `token_readonly`, `server_not_stopped` and the like stay plain errors. A type that Hetzner's own list marks as not orderable in the location counts too, before anything is sent.
- **The message keeps Hetzner's code and message verbatim** and says what is left. For most refusals it says Hetzner may be limiting servers for the account or the location. `resource_limit_exceeded` is the project's own limit, in every location: the message says so, names the two fixes (a higher limit from Hetzner, or a server deleted), and up offers another cloud first and no other location or size.
- **A refused create deletes the firewall it made**, when nothing is attached to it. The box has no server, so the firewall serves nothing; a box that moves to another cloud would leave it in the project for good. The next create makes it again. A firewall that was there before the create, or that has anything attached, stays as it is, and the message says where to delete it. The project SSH key stays: it is the laptop's, and other boxes use it. A refused resume keeps the firewall, which the parked box keeps with its rules, and the snapshot.
- **Until a box's server exists, up keeps its answers in its progress file** (`Answers`, the flags that give them, no secrets), and `keelbox up BOX --provider OTHER` configures it on another cloud with them. The answers that hold for one cloud only (provider, location, size and the cloud's sign-in) are not carried. Only that cloud's questions are asked, and the go-ahead, unless `--yes` is given. On Hetzner, `--location` (checked against Hetzner's list of locations) and `--size` change where the server is created.
- **Only a create that certainly made nothing marks a box as having no server**: a refusal, or a failure before the order is sent (the server types, the image, the SSH keys, the firewall). The progress file marks the create as started before it runs, whether `keelbox up` or `keelbox create` runs it, and clears the mark after such a failure. Any other failed create leaves the server possibly existing, as before: `--provider`, `--location` and `--size` then change nothing, with the warning they always had, and `keelbox up BOX` or `keelbox destroy BOX` go on from there.
- **Before a move or a change of location or size, up asks the cloud** whether it has a server keelbox created for the box. If it has, nothing changes: up records the server, so `keelbox up BOX` sets it up there, and the error says to delete it first (`keelbox destroy BOX`) to go elsewhere. `--size` is checked against Hetzner's list of server types, as `--location` is against its locations, before the config changes.
- **On a terminal, up asks after a refusal**: another location (with the size's price there beside the price the go-ahead showed, then a size if the one asked for is not sold there), another size in the location (the nearest of the same architecture with at least the cores and memory asked for first, then the smaller ones, largest first), another cloud, or stop. Without a terminal it prints one command for each, each as it runs. Another location or size is created without another go-ahead, so each one printed carries its monthly price. A move to another cloud prints no `--yes`: it stops at that cloud's go-ahead, which shows the price and the command with `--yes`. A `--yes` given for Hetzner does not carry to another cloud in the same run.
- **During a move, every command up prints is the move's own**: the command as it was given (`--provider`, `--location`, the cloud's sign-in flags), with what is missing added.
- Resize and resume print the next step for their case: the box keeps its size, or stays parked, and the config keys or `keelbox resize` say how to try elsewhere or later.

## Consequences
- A user whom Hetzner turns away gets to a running box on another location or cloud in the same `keelbox up`, without answering the rest again.
- If Hetzner uses a code keelbox lists as not a refusal, the user sees the plain API error as before.
- The up progress file holds the answers until the server exists. They are the values of flags, which carry no secrets.

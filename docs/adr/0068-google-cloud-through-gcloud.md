# 0068: Google Cloud through the user's gcloud

Date: 2026-11-13. Status: accepted. Follows [ADR 0065](0065-aws-through-the-aws-cli.md) and [ADR 0067](0067-digitalocean-through-doctl.md).

## Context
The AWS and DigitalOcean providers run the cloud's own CLI ([ADR 0065](0065-aws-through-the-aws-cli.md), [0067](0067-digitalocean-through-doctl.md)): keelbox holds no credential, adds no SDK and reads JSON. Google Cloud's CLI, `gcloud`, fits the same pattern, and a Google sign-in (a user account, a service account, workload identity, impersonation) is not something keelbox should reimplement or hold.

Google Cloud differs from the other three in ways that shape the design. Facts it relies on, read 2026-11-13 in the help of the gcloud 593.0.0 binary, Google's Compute Engine and VPC documentation, the source and README of Google's guest agent (`GoogleCloudPlatform/guest-agent`) and cloud-init's `DataSourceGCE`; the commands, flags, JSON and error texts were also run through the gcloud 593.0.0 binary against a stub of the API (`internal/provider/gcp/realcli_test.go`):
- **Sign-in and project.** gcloud keeps its sign-in and a default project and zone in its own configuration; `gcloud config list --format=json` prints them without a network call. Every Compute Engine command takes `--project`. `CLOUDSDK_AUTH_ACCESS_TOKEN_FILE` and `CLOUDSDK_API_ENDPOINT_OVERRIDES_COMPUTE` exist, which is what the contract test uses.
- **Output and errors.** With `--format=json` a command prints JSON on standard output. An error is text on standard error, `ERROR: (gcloud.compute.instances.create) Could not fetch resource:` and a line per cause with the API's message; there is no status code. `gcloud compute instances list`, `addresses list` and `machine-types list` gather several requests, and when one fails they print `WARNING: Some requests did not succeed`, an empty or partial list, and exit 0. gcloud follows the API's pages itself.
- **VMs.** `gcloud compute instances create NAME --zone --machine-type --image-family --image-project --boot-disk-size --labels k=v --tags --address --metadata k=v --metadata-from-file KEY=PATH --no-service-account --no-scopes`. Names are unique in a zone, not in a project, start with a letter and have at most 63 characters. Labels are keys and values. The command returns when the VM is running. Without `--no-service-account` a VM gets the project's default service account, whose token every process on the VM can read from the metadata server and which, depending on the organisation, has the Editor role on the project.
- **Image.** Canonical publishes Ubuntu in the project `ubuntu-os-cloud`; the family for 24.04 LTS on x86 is `ubuntu-2404-lts-amd64`. Its default boot disk is 10 GB. The image runs cloud-init, which reads the metadata key `user-data`, and Google's guest agent.
- **The guest agent** creates accounts from SSH keys in the project's and the VM's metadata (`ssh-keys`), with sudo through the group `google-sudoers`, unless OS Login is on (`enable-oslogin=TRUE` in project or VM metadata, or the organisation policy `compute.requireOsLogin`), in which case IAM decides who logs in. `block-project-ssh-keys=true` on a VM stops the project's keys there; cloud-init's GCE datasource honours it too. On a VM's first boot the agent **generates new SSH host keys**, replacing those present, unless `set_host_keys = false` is in `[InstanceSetup]` of `/etc/default/instance_configs.cfg`. Its unit starts after `network-online.target` and before sshd, "in order to regenerate SSH host keys"; cloud-init writes files and host keys before `network-online.target`.
- **Firewall.** A VPC network has rules, not a firewall object per VM. A rule has a priority (0 to 65535, lower wins, default 1000), an action, source ranges and target network tags, and carries no labels. "A rule with a deny action overrides another with an allow action only if the two rules have the same priority." The `default` network comes with `default-allow-ssh`, `default-allow-rdp`, `default-allow-icmp` and `default-allow-internal` at priority 65534, applying to every VM in it. Outbound traffic is admitted unless a rule refuses it. `gcloud compute firewall-rules update` changes only the fields it names, and cannot change the action.
- **Address.** "Ephemeral IP addresses are released if you stop or delete the associated resource." A reserved (static) regional address keeps its value; it carries a name and a description, and `gcloud compute addresses create` takes no labels. It lists what uses it (`users`).
- **Price.** gcloud has no command that prints the price of a machine type.

## Decision
- **Provider `gcp` runs the user's installed gcloud.** `internal/provider/gcp` executes `gcloud ... --format=json --quiet` and reads the JSON. keelbox holds no Google credential and adds no SDK. The config names a project (`target.gcp.project`, passed as `--project`), a zone and a machine type. Without a project keelbox uses the one gcloud is configured for; `keelbox up` always writes the project into the config, so a box stays in its project whatever gcloud points at later. There is nothing for `keelbox forget-token` to remove.
- **A box is one Compute Engine VM** named after the box, labelled `keelbox=true` and `keelbox-box=<box>` (`provider.ManagedLabels`), from the image family `ubuntu-2404-lts-amd64`, in the network `default`, with a balanced persistent disk of `target.gcp.disk_gb` (default 50 GB, because 10 does not hold Docker images and a few projects). `Find` and `Destroy` touch a VM only when it is named after the box and carries both labels. `create` fails when a VM of the box's name exists in any zone, so names stay unique in the project. Box names for this provider start with a letter and have at most 49 characters, which leaves room for the names below.
- **No service account.** The VM is created with `--no-service-account --no-scopes`, so nothing on it, the agent included, can get a token for the project from the metadata server.
- **A partial list is an error.** Any gcloud output that says `Some requests did not succeed` is treated as a failure, exit code 0 or not. A refused or failed request therefore never reads as "no VM" or "no address".
- **Errors are told apart by Google's wording**, since gcloud gives no status: no account or an expired sign-in (`gcloud auth login`), no project (`gcloud config set project`), the Compute Engine API off (`gcloud services enable compute.googleapis.com --project ...`), no billing account, a project the sign-in cannot use, a resource that is not there. An error keelbox does not recognise is shown as gcloud printed it.
- **First contact is verified, and the first login is the admin.** The host key is generated on the laptop, pinned before the VM exists and installed by cloud-init, as on the other clouds (ADR 0007); `RotateHostKeys` replaces it after the first verified connection. The user data is the cloud-config of `provider.AdminUserData` (the admin account with the user's keys and passwordless sudo, `ssh_pwauth: false`, `disable_root: true`) plus one `write_files` entry that appends `set_host_keys = false` to the guest agent's configuration, so the agent does not replace the pinned key on first boot. It goes to gcloud as `--metadata-from-file user-data=PATH`, a mode 600 temporary file removed afterwards, never as an argument. If the agent replaced the key all the same, keelbox would refuse the VM's key and `create` would fail: it never falls back to trusting what the VM presents.
- **Not OS Login, not metadata SSH keys.** The VM's metadata sets `enable-oslogin=false` and `block-project-ssh-keys=true`. keelbox adds no key to the project's or the VM's metadata, so there is none to remove. Two other ways in were rejected: OS Login makes the project's IAM, not the box's config, decide who has an account and sudo on the box; project `ssh-keys` metadata gives every key in the project an account with sudo on every VM. Where an organisation enforces `compute.requireOsLogin`, `create` fails and says so.
- **Two firewall rules per box, on the box's network tag.** `keelbox-<box>-allow` (priority 900) admits UDP 41641 always and TCP 22 until the box has closed public SSH ([ADR 0022](0022-hetzner-cloud-firewall.md)); `keelbox-<box>-deny` (priority 901) refuses every other inbound IPv4 packet. Both apply to the tag `keelbox-box-<box>` only, which the VM is created with, and both exist before the VM. One allow rule alone would not do what the other clouds' firewalls do: the `default` network's own rules admit SSH from anywhere to every VM, so "closing public SSH" would close nothing. The deny rule sits ahead of those rules (65534) and of rules made at the default priority (1000). Outbound traffic needs no rule.
- **A reserved address.** `create` reserves a regional external address named `keelbox-<box>` and gives it to the VM, because the address Google otherwise lends changes when the VM is stopped and started, and the box's pinned host keys, its config and `keelbox ls` go by that address. The same choice as on Lightsail, and unlike DigitalOcean, where a Droplet keeps its address.
- **Rules and addresses are known by name and description.** They carry no labels. keelbox changes or deletes a firewall rule only when it has the box's rule name, the description keelbox writes ("Managed by keelbox: the allow rule of box ...") and the box's tag as its only target; an address only when it has the name `keelbox-<box>` and keelbox's description, and nothing uses it. One of those names that fails the check stops the command: keelbox did not make it and does not touch it.
- **Destroy leaves nothing.** It deletes the VM (its boot disk goes with it), then the two rules, then releases the address. With no VM, `destroy` still removes the rules and the address an interrupted `create` left, and only when no VM carries the box's tag or label.
- **No price is shown.** `keelbox up` lists the E2 machine types up to 8 vCPUs with their cores and memory, says that gcloud has no price list, and names Google's pricing page. The summary before the go-ahead says the same instead of an amount. keelbox does not ship a price table: it would be wrong the day Google changes a price.
- **Preflight names the fix**, before anything is created: gcloud missing, the cases above, a zone that is not up (the zones of its region), a machine type the zone lacks or an Arm one (some that exist), a project without a `default` network (`gcloud compute networks create default --subnet-mode=auto`).
- **doctor checks the cloud side from the laptop**: both rules exist as keelbox writes them and match the box's SSH state; the VM still carries the tag; its metadata still blocks project keys, has OS Login off and holds no SSH keys, and no service account is attached. It warns, without changing anything, when another rule of the network admits traffic to the box ahead of the deny rule.

## What the credential can reach, and what is checked
- gcloud's sign-in can do whatever its account is allowed in the project, and in every other project it can reach; keelbox cannot narrow it. keelbox itself runs `config list`, `compute project-info describe`, the zone, machine type, network, firewall rule, address and instance lists, and creates, updates and deletes only the box's labelled VM, its two rules and its address. That is enforced by keelbox's own code and covered by tests against a fake gcloud (`TestNeverTouchesWhatItDidNotMake`), not by Google.
- To have Google enforce more, use a project that holds only boxes, and a sign-in whose role there is Compute Admin (`roles/compute.admin`) and nothing else. IAM does not limit by label or by name here.
- Anyone who can change the VM's metadata in the project can still get onto the box outside keelbox: the guest agent creates an account with sudo for a key added to the VM's `ssh-keys` metadata, and runs a `startup-script` as root at the next boot. keelbox does not turn the agent's account handling off; `keelbox doctor` reports such keys when it runs. This is the cloud account's power over its own VM, as on every cloud.
- The host key never reaches a command line: a test fake fails if it appears in an argument and checks the file's mode, and the contract test checks that the real gcloud reads the file.

## Consequences
- Google Cloud needs gcloud on the laptop. Without it `keelbox up` says how to install it and stops (exit 3 without a terminal).
- A command that reaches Google Cloud costs one `config list` and one `project-info describe` more than it strictly needs, so that a missing sign-in, project or API is reported with its fix. Each gcloud call takes a second or two to start.
- The box takes no inbound traffic that keelbox's allow rule does not admit: not from other VMs of the network, not ICMP, not Google's SSH-in-browser or Identity-Aware Proxy ranges. To open a port to the box, add a rule for its tag with a priority number below 901. Firewall policies of the organisation, a folder or the network are evaluated outside these rules and keelbox neither reads nor changes them.
- The deny rule covers IPv4. The VM is created without an IPv6 address, as keelbox connects over IPv4.
- The reserved address is billed by Google, also while the VM is stopped, and counts against the region's quota of static addresses. `keelbox forget` says that it stays.
- Only x86 machine types, only the `default` network, and one image family.
- `target.gcp.project` unset in a hand-written config means "whatever gcloud is configured for at the time", which can change between commands. Labels still keep keelbox from touching another project's resources; the box is just not found there.
- Tested against the fake, with the real gcloud against a stub API, and end to end on a real account (`make e2e-gcp`). keelbox matches gcloud's errors (an expired sign-in, a project without billing, an organisation that requires OS Login) by their text, which Google may change.
